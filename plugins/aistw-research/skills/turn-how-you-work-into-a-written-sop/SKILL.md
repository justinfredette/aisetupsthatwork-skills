# Turn how you work into a written SOP

## When to use

Owners and solo operators who need to hand off repeat work to a helper, VA, or first employee.

## Steps

1. Pick one repeat task. Do it once slowly and narrate every action out loud; record or jot notes.
2. Feed the rough notes into the prompt below to get a structured SOP draft with header, steps, and exception notes.
3. Review the draft against reality. Fix any step a beginner could read two ways.
4. Hand it to someone unfamiliar and say nothing. Every place they stop to ask is a gap; fill it.
5. Add a header: process name, owner, last-updated date, tools required. Date every revision.
6. Store SOPs in one shared folder and review them when the process changes, not on a calendar.

## Prompt

Fill the [BRACKETED] parts with the user, then follow this prompt:

```
Here are my rough notes on how I do this task: [PASTE NOTES]. Turn them into a standard operating procedure with: 1) a header (process name, owner: [NAME], tools required), 2) numbered steps with exactly one action per step, written for someone who has never done this, 3) two or three exception notes for common edge cases. Use plain language, no jargon. Show me the draft so I can correct it.
```

## Guardrails

- Draft first and show the user. Never send, post, pay, book, cancel or delete without the user's explicit approval of that exact action.
- Use only facts the user gives you or that you can cite. If something is missing, ask instead of guessing.

## Common snags

- AI fills gaps with plausible guesses. Correct every step against how you actually do the work.
- An SOP nobody tests is fiction. The unfamiliar-reader test is the whole quality check.
- Screenshots and exact button names beat paragraphs. Add them where the UI matters.
